# Rules.md
## Ground rules for any AI coding assistant (Claude Code, Cursor, etc.) working on this project

These rules exist to keep the project honest, scoped, and aligned with what the Razorpay judges will actually evaluate. Read this file before generating or modifying any code in this repo.

---

## 1. Non-negotiable project rules

- **Never fabricate a metric.** Every accuracy, recovery rate, or comparison number shown anywhere (code output, dashboard, docs) must come from an actual run against real data in this project — never a hardcoded or invented placeholder left in "for now."
- **Never let Stage 1 or Stage 2 silently become LLM calls.** These stages must use the trained ML models (scikit-learn/XGBoost) defined in architecture.md. If you find yourself about to add an LLM call to these stages "to make it easier," stop — this breaks the project's core differentiation.
- **Never remove the hard stopping rules.** Max 4 retries per payment in 30 days, and the mandatory 24-hour RBI pre-debit notice window, must remain enforced in code at all times, not just mentioned in comments.
- **Never let the promise-tracker escalation loop run unbounded.** There must always be a final "stop" state in the escalation ladder.
- **Never touch Stage 4 (Hinglish voice) before Stages 1–3 pass their end-to-end test.** Check plan.md's current stage status before starting any voice-related code.

## 2. Data rules

- Do not claim data is "real" if it was generated by Faker — always keep clear separation in code and comments between the real Kaggle-derived distributions and the synthetic labels layered on top.
- Ground-truth labels used for evaluating Stage 1/2 accuracy must be kept separate from what the model sees as input — the model must never be trained directly on its own evaluation label as a feature.
- Any dataset file downloaded from Kaggle stays out of version control (add to `.gitignore`) — it's the user's local download, not something to commit to the public GitHub repo.

## 3. Code style and structure

- Python backend: FastAPI, organized by stage (`stage1_diagnosis/`, `stage2_retry/`, `stage3_promise/`, `audit/`) rather than one giant file.
- Every ML training script must do a proper train/test split and must print/save the evaluation metrics — never train and skip evaluation.
- React frontend: functional components only, Tailwind for styling, Recharts for all charts. No inline styles, no CSS files unless truly necessary.
- Keep API keys and database connection strings in a `.env` file, never hardcoded in source. Add `.env` to `.gitignore`.

## 4. Compliance-mindedness (this is graded, not decoration)

- Any customer-facing message text (reminders, retry notices, escalation messages) must be polite and must never simulate harassment-style repeated contact.
- Retry and escalation logic must always be explainable — if asked "why did the agent do X," the audit trail must have the answer.

## 5. Honesty in the "what broke" story

- Keep a running `CHANGELOG_ISSUES.md` (or similar) noting real bugs/wrong assumptions hit during development, updated as you go — not reconstructed from memory on the last day. This is explicitly part of what Razorpay's judges evaluate.

## 6. Scope discipline

- Before adding any feature not listed in prd.md or plan.md, check whether it's actually needed to hit the success metrics in prd.md — if not, it's scope creep and should be flagged, not silently built.
- Streamlit, SQLite, or any tool explicitly replaced during planning (see memory.md) must not reappear in the codebase — those decisions were made deliberately after weighing tradeoffs.

## 7. When in doubt

- Re-check plan.md for what day/stage the project is currently on.
- Re-check architecture.md for why a given stage uses ML vs. LLM before changing that choice.
- Re-check memory.md for the reasoning behind past decisions before reversing them.
